# ADR 0026: Node.js 26

- **Status:** proposed
- **Date:** 2026-10-27
- **Deciders:** Aaron Gardner

## Context

[ADR 0001](0001-monorepo-toolchain.md) pins Node.js 24.21.0 and plans the move
to Node.js 26 "once it has settled as LTS", in its own short ADR. Node.js 24
went into maintenance on 20 October 2026. Node.js 26 becomes LTS on
28 October 2026 and is supported until 30 April 2029.

Node.js 25 and later no longer bundle Corepack, which today makes the `pnpm`
command available at the version in `packageManager`.

The release-age rule (7 days, ADR 0001) applies to the runtime too. On
27 October the newest 26.x is 26.12.1, a security release dated 21 October
(6 days old); 26.12.0, dated 14 October, is the newest that is 7 days old.

The runtime is pinned in five places:

- `.node-version`, which CI's `setup-node` reads;
- `devEngines.runtime` in the root `package.json` (a warning on a mismatch);
- `engines` in the root `package.json`, which `engineStrict` enforces;
- `@types/node` in every manifest that has it;
- the base image tags in `infra/docker/`.

## Options considered

Runtime:

1. **Stay on Node.js 24 until April 2027.** No change now, but the runtime
   gets only security fixes from 20 October, and the move still has to happen
   while V1 is being built.
2. **Move to Node.js 26 now.** 30 months of support from LTS. Node.js 26
   bundles undici 8, the line the outbound dispatcher pins. Costs a separate
   Corepack install.

The pnpm launcher on Node.js 26:

3. **Install Corepack at an exact version** (`npm install --global
   --ignore-scripts corepack@0.36.0`) before `corepack enable`, in CI, the
   images and developer set-up. Keeps today's behaviour: `packageManager` and
   its integrity hash choose pnpm, and Corepack checks the hash.
4. **Let pnpm manage its own version.** A globally installed pnpm switches to
   the version in `packageManager`. One fewer tool, but every machine first
   needs some pnpm from somewhere, and that install is not pinned by the
   repository.

## Decision

Options 2 and 3.

- Node.js 26.12.1 in `.node-version` and `devEngines.runtime`. It is a
  security release, 7 days old on 28 October and so before this change can
  merge; pinning 26.12.0 would mean pinning a release with known fixes
  missing. The next pin follows the 7-day rule as usual.
- `@types/node` 26.6.5 in every manifest that has it.
- Root `engines` accepts both lines, `>=24.16.0 <25 || >=26.12.1 <27`, until
  the base images move to Node.js 26. Then it narrows to the 26 line.
- Corepack 0.36.0, installed with `--ignore-scripts` before `corepack enable`
  in every CI job, in the images and in the developer set-up.

## Consequences

- Developers install Node.js 26.12.1 and then Corepack 0.36.0. The README
  and the self-hosting quickstart say so.
- The base images move to `node:26.12.1` with their own digest, which must be
  7 days old.
- Corepack's version is one more pin to update each month. Dependabot does
  not see it, so the monthly batch checks it by hand.
- On Node.js 26 the npm `undici` package and the bundled one share a major,
  so `setGlobalDispatcher` from the package also governs the global `fetch`.
- ADR 0001's runtime lines are read with this ADR: Node.js 26 replaces 24,
  and Corepack is no longer bundled.

## Base image

The API, console and portal images move off Debian 12 with Node.js 26.
Trivy 0.74.0 counts for HIGH and CRITICAL findings, scanned on 29 October
2026 (vulnerability database of 22 October):

| Image | All | With `--ignore-unfixed` |
| --- | --- | --- |
| `node:24.21.0-bookworm-slim` (today's base) | 69 high, 4 critical | 12 high, 3 critical |
| `node:26.12.1-trixie-slim` | 47 high | 3 high, all in the bundled npm |
| `gcr.io/distroless/nodejs26-debian13` | none | none |

The runtime stage deletes npm, so the Debian 13 slim runtime image has no
fixable finding. Its unfixed ones are in util-linux, ncurses, systemd
libraries and perl-base, none of which the servers call.

1. **Debian 13 slim.** Pinned to the exact Node.js version in
   `.node-version`. It keeps the `node` user (uid and gid 1000) and a shell,
   so `docker exec` debugging, the runtime stage's clean-up and the Compose
   health checks all carry over with no Compose change.
2. **Distroless.** No shell or package manager, and the fewest findings.
   But its only tag follows the newest 26.x (26.13.0 on 29 October), so the
   image cannot be pinned to the version in `.node-version`; it runs as root
   or uid 65532 unless set to `1000:1000`; and there is no shell for
   debugging or for a clean-up step.

Decision: Debian 13 slim, `node:26.12.1-trixie-slim`, in every stage. We
look at distroless again if it publishes tags per Node.js version.

The only digest the tag serves on 29 October,
`sha256:94816674c62774da0d099a947bf4613b9e1972a2733abd0d0cd80e795f8411d0`,
was built on 28 October, so under the 7-day rule it can be adopted from
4 November 2026. The images keep their Debian 12 base until then. Root
`engines` narrows to the 26 line in the same change that moves the images.
